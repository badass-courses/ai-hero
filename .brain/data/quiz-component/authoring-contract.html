AI Hero · authoring contract

Writing quizzes in a lesson body

Everything an agent needs to generate a working <Quiz> for an AI Hero lesson. Quizzes are authored inline in the lesson MDX — there is no separate record to create first and no API call to make.

The shape

Copy this. It is the whole contract.

<Quiz>
  <QuizQuestion data={{
    id: "agent-fix-verification",
    question: "What is the strongest first move when an agent reports that a bug is fixed?",
    type: "multiple-choice",
    choices: [
      { answer: "a", label: "Ask it to explain the code in more detail" },
      { answer: "b", label: "Reproduce the original failure and run the relevant check" },
      { answer: "c", label: "Accept the fix if the diff looks reasonable" }
    ],
    correct: "b",
    answer: "A plausible diff is not proof. Reproducing the failure first gives you a baseline, and rerunning the same path after the change proves the behavior actually changed."
  }} />
</Quiz>

Put as many <QuizQuestion> children inside one <Quiz> as you like. The wrapper renders the heading and spacing; each question grades independently.

Fields

FieldRequiredTypeNotes
id Yes string Stable identifier. See Choosing ids — this is the one field that will hurt you later if you get it wrong.
question Yes string The prompt. Non-empty.
type Yes "multiple-choice" This exact literal. No other value is accepted today.
choices Yes array At least 2. Each is { answer, label?, image? }. answer values must be unique within the question — they are the identity of each option, so keep them short and stable ("a", "b").
correct Yes string or string[] Must match choices[].answer values. An array turns on multi-select. Values must be unique.
answer Yes string The explanation shown after the learner answers. Non-empty. This is where the teaching happens — make it earn its place.
allowMultiple No boolean Forces checkboxes even when correct is a single string. Use when exactly one answer is right but you want the learner to consider combinations.
shuffleChoices No boolean Choices shuffle by default on any graded question. Set false to preserve your authored order — needed for "all of the above" or ordered options.

Rules that will reject your output

These are enforced, not advisory. Two layers check your work: the renderer validates on the page, and the content sync validates before publish.

  • Missing id — sync fails; the page renders but warns and saves nothing.
  • Duplicate id — within a lesson or across lessons. Ids are globally unique.
  • A correct value with no matching choice — the classic answer-key typo. Caught before a learner sees it.
  • Duplicate choice answer values, or duplicates inside correct.
  • Fewer than 2 choices.
  • Empty question, answer, or any choice answer — whitespace-only counts as empty.
  • Anything non-static in data — see below.

Write a literal object. Nothing computed.

The sync reads your data by parsing the source, not by running it. Only plain literals survive: strings, numbers, booleans, arrays, nested objects.

These all fail:

<QuizQuestion {...props} />              {/* spread — rejected outright */}
<QuizQuestion data={questionData} />     {/* variable reference */}
<QuizQuestion data={{ ...base, id: 1 }} /> {/* spread inside the object */}
<QuizQuestion data={{ question: makeQ() }} /> {/* function call */}
<QuizQuestion data={{ correct: x ? "a" : "b" }} /> {/* conditional */}

Spreads are rejected loudly rather than skipped, because a spread renders a real question the learner can answer while nothing extractable reaches the database — the stored quiz would silently disagree with what is on screen.

Choosing ids

The id is the permanent identity of a question. Everything else about a question can change; the id should not.

Why it matters

Answers are keyed to the id, not the question text. That is deliberate: it means you can fix a typo, tighten the wording, or rewrite a question entirely and the answer history stays attached.

Change the id and you fork the history. The old answers stay in the database attached to an id nothing references anymore, and the question looks brand new. Nothing errors. You would find out from a chart that quietly stopped making sense.

Answers are being recorded now, so this is live rather than theoretical — every id you write today is the key its answer data hangs off.

Good ids describe the concept being tested, so a rewrite naturally keeps the same one:

  • agent-fix-verification
  • prompt-specificity-checkout
  • narrow-diff-preference

Bad ids encode something that changes:

  • question-1 — breaks the moment you insert a question above it
  • lesson-3-q2 — breaks when the lesson moves
  • what-is-the-strongest-first-move — breaks when you reword

Ids are unique across the whole course, not just one lesson. If a question genuinely belongs in two lessons, give each its own id.

Single answer vs multi-select

A question is multi-select when correct is an array, or when allowMultiple: true. Otherwise it renders radios.

{/* radios — one right answer */}
correct: "b"

{/* checkboxes — two right answers, both required */}
correct: ["a", "c"]

{/* checkboxes, but only one answer is right */}
correct: "b",
allowMultiple: true

Grading is exact-set. All or nothing.

For correct: ["a", "c"], a learner who selects only "a" is marked wrong. So is one who selects "a", "b", and "c". Order does not matter.

There is no partial credit. If you write a five-option question with three correct answers, most learners will get it wrong. That may be what you want — just choose it on purpose.

What a learner sees

  1. The question with its choices, shuffled unless you set shuffleChoices: false.
  2. They select and submit.
  3. Each choice is marked correct or incorrect, and your answer explanation appears.

Quizzes are open to everyone. No login is required to answer, and a logged-out learner gets the same grading and the same explanation.

What gets saved

Answers are recorded so you can see which questions people miss. This is the part your id choices have been feeding all along.

LearnerSees gradingAnswer recorded
Logged inyesyes
Logged outyesno
Question has no idyesno

Answering is never gated; only saving is. A logged-out learner still gets the full teaching moment — grading, correct/incorrect marking, and your explanation. Their answer just is not stored.

Grading is graded on the server

The browser shows the result immediately, but what gets recorded is decided server-side against the answer key stored with the question. The page cannot tell the database that a wrong answer was right.

This is why a question must be synced before its answers can be saved. If you add a quiz and answer it before the content sync has run, the grading still shows — the answer just is not recorded. It starts recording once the question syncs.

Changing an answer

One record per learner per question. If the same learner answers a question again, the new answer replaces the old one rather than adding a second record. Refreshing the page clears the on-screen state and lets them answer again.

Saving is best-effort and never blocks the learner. If a save fails, they still see whether they were right and still get the explanation — the failure is logged on our side, not shown to them.

When authoring goes wrong

A bad quiz never breaks the lesson around it. The failure surfaces differently depending on where it is caught:

ProblemCaught atWhat happens
Missing or duplicate id, spread, non-static data, schema violation Content sync Sync fails and names the lesson and the offending id. Nothing publishes.
Invalid data that reaches the page anyway Render That one question becomes an inline error box. The rest of the lesson is untouched. Outside production, the exact validation issues are listed.
Missing or duplicate id at render Render The question works normally but warns that answers will not be saved.

Not supported yet

  • Question types other than multiple choice. No free-text or essay questions.
  • Images in choices. The image field exists in the schema but the component does not render it.
  • Scoring. Questions grade individually. There is no "you got 7 of 10".
  • Partial credit on multi-select.

A complete example

<Quiz>
  <QuizQuestion data={{
    id: "prompt-evidence-quality",
    question: "Which prompt gives an agent the best chance of diagnosing a failing checkout?",
    type: "multiple-choice",
    choices: [
      { answer: "vague", label: "Checkout is broken. Fix it." },
      { answer: "broad", label: "Rewrite the checkout so it is more robust." },
      { answer: "specific", label: "On the payment step, clicking Pay returns HTTP 500. Here is the exact error, the expected result, and a test account." }
    ],
    correct: "specific",
    answer: "The third prompt supplies a reproducible action, observed behavior, expected behavior, and concrete evidence. That lets the agent investigate instead of guessing what 'broken' means."
  }} />

  <QuizQuestion data={{
    id: "review-report-contents",
    question: "Which of these belong in the report after an AI-assisted change? Select all that apply.",
    type: "multiple-choice",
    shuffleChoices: false,
    choices: [
      { answer: "files", label: "The files that changed" },
      { answer: "checks", label: "The checks that were run and their results" },
      { answer: "risk", label: "Any remaining risk or unverified assumption" },
      { answer: "transcript", label: "A full transcript of every reasoning step" }
    ],
    correct: ["files", "checks", "risk"],
    answer: "A useful report leaves receipts: where the change lives, what was verified, and what still needs judgment. The full transcript buries all of that."
  }} />
</Quiz>

Quizzes are authored inline in the lesson body and flow through the normal content sync — no schema change, no separate authoring step. Content sync derives a question record from each <QuizQuestion>, which is what makes answers reportable once persistence lands.
