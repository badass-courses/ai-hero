# Desk C5 coupon batches

Off by default. The desk can issue C5 comps without a production database credential. The old support mint route is unchanged.

## Wire contract

All calls are under `/api/commerce/coupon-batches`. Send an expiring desk PAT in `Authorization: Bearer …`. Commerce scopes are not available through self-service PAT minting. A separate server-side desk grant controls `commerce:coupons:mint` and `commerce:coupons:read` for each principal.

1. `POST /preview` with `campaignRef`, `templateId: "c5-comp-v1"`, `template: { productId: "product-s00zs", percentageDiscount: 1, maxUses: 1, deadlineAt }` and `items: [{ intentKey }]`. `deadlineAt` is an absolute, whole-second instant in the next 30 days. The response includes normalized terms, `eligible`, `alreadyMinted` and `refused` counts, an initial page of verdicts and a confirmation receipt. Matching terminal mints are `already_minted`, not new eligible work. Preview writes nothing.
2. Confirm the terms. `POST` the same manifest with `previewReceipt` and an `Idempotency-Key` header. The receipt binds the normalized body, desk principal and policy version for five minutes. New batches return `202` after the whole request is durable. Minting runs only in the worker. Follow `Location` or replay the same key and manifest. A different manifest under the same key conflicts. A replay of an accepted manifest needs no new receipt and returns status even while new admissions are paused.
3. `GET /{batchId}?cursor=N` for up to 100 outcomes and aggregate counts. `POST /lookup` with `{ intentKeys: [...] }` for at most 100 keys. A pending item is not unknown. Duplicate intent keys inside one manifest are invalid. If a batch cannot mint because its credential, policy, deadline or export window is no longer valid, unminted keys can be submitted again in a new confirmed batch with a new request key and valid terms. Status and lookup never return redemption codes.
4. `POST /export` with `{ batchId, cursor? }` after completion, or while the batch is stopped or parked. A stopped or parked export returns only codes already committed, never a code for pending work. Resume scanning from cursor zero after progress, because a previously queued row may have minted. Only the initiating desk principal can export, with the read grant and a valid PAT. The response is private and no-store. Codes stop exporting after 24 hours or coupon expiry, whichever comes first. A second batch that references the same intent cannot extend that window. Successful export pages commit a durable `AI_CouponBatchExportAudit` row with the principal, batch, time and number of codes returned, including zero. An unavailable decryption key or failed authentication of an item yields `export_code_unavailable` for that item only; its mint status does not change.

Preview and submit accept up to 12,000 items and 4 MiB of request body. Above either hard input limit they return `413 manifest_too_large` without admitting a partial manifest. The volume alarms below those limits still do not refuse requests.

Codes transfer until spent or expired. Open a C5 `?code=` link to exchange the selector before rendering HTML. The private `303` removes the query and saves two one-hour HttpOnly cookies: one scoped to that cohort, one scoped to `/api/coursebuilder/redeem`. Both are Secure in production. Valid claims render a dedicated $0 offer, not a paid quote from `prices-formatted`. The clean page passes no selector to HTML, RSC, the pricing component or sign-in `callbackUrl`. Other pages drop the reserved `code` without setting cookies. Client analytics see the clean URL; Sentry and OpenTelemetry scrub selectors in app telemetry. The raw entry URL and cookie headers still reach infrastructure before these checks. Do not enable link delivery until hosted ingress, access logs and browser capture are verified.

The browser submits only an inert marker to the existing free claim route. The server resolves it from the scoped cookie and removes the cookie and bearer before invoking Course Builder. Direct claims may still submit the code in the JSON body, never in a checkout URL or Stripe metadata. Comp claims require `Content-Type: application/json` with a single C5 `productIds` value. Ordinary claims retain Course Builder’s parsing. Do not copy codes into receipts, logs or support transcripts. Coupon refs in status are not selectors. The template owns the C5 sold-out bypass; a different product cannot borrow it.

## Enable and stop

Deployment, grants and live minting each need approval.

- Paid coupon backfill done (receipt `2026-11-27T03-20Z`): the desk counted 158 uses. Confirm the receipt before the dependency rollout.
- Before flipping the batch gates, verify no existing coupon ID or code, or purchase coupon reference, begins with `c5comp_`, `batch-coupon-`, or `c5hash_`. The desk’s read-only pre-check found zero coupons and zero purchase references.

Apply `src/db/migrations/20261126_ai_hero_coupon_batches.sql`, `src/db/migrations/20261127_ai_hero_coupon_batch_export_audit.sql`, then `src/db/migrations/20261128_ai_hero_coupon_batch_claim_stop.sql` through the reviewed schema path. `claimsEnabled` defaults to zero; opening issuance does not open claims. Leave `AIH_COUPON_BATCH_ENABLED` unset and both `AI_CouponBatchControl` rows absent or disabled until rollout. Provision `ai-hero` with `enabled=0` for issuance and `ai-hero-claims` with `claimsEnabled=0` for claims. Each gate reads only its own row; a missing row fails closed. Store a strong, dedicated `AIH_COUPON_BATCH_SECRET` server-side for preview signing and export encryption. Do not rotate it during an active export window unless losing export access is acceptable; redemption does not depend on the key.

Admission persists the complete manifest atomically in statements of up to 100 rows before returning `202`. The submit route declares `maxDuration = 60`. At the 12,000-item limit it spools up to 4 MiB and writes 120 manifest pages plus the batch and request-alarm rows in one transaction; no coupon is minted inline. The manifest rows are not separate jobs. The worker expands only the next eligible chunk into mint candidates, drains at most 100 rows per transaction, and uses one DB connection per issuer process, separate from checkout. The issuer pool sets UTC, a 15-second server idle timeout, and a 5-second lock wait timeout, and closes idle client sockets before the server timeout. If a required session setting is rejected, the pool destroys that socket and refuses work until a bounded exponential cooldown expires. A new socket must pass every session setting before it can serve work. The pool queues at most four acquisitions and stops waiting after 1.5 seconds. Saturated desk HTTP calls receive a code-free, retryable `503 coupon_batch_unavailable`; retry submit with the same idempotency key. Validate these settings on the deployment database before turning on the flag. Customer claims use the normal application pool and a coupon-row transaction, with no new Vitess session variable or lock timeout. Verify the configured database supports that locking path before enabling claims. The control row sets `chunkSize` and `paceMs` without a redeploy. Change those before adding concurrency. A `202` batch survives missed wakes; a once-per-minute sweep finds due work. The drain queues continuation steps rather than skipping overlapping wakes. A paced wake with no progress exits immediately. A run can sleep only after advancing the cursor, and stops if it wakes still paced. Only a window ending in progress sends another wake. The database control row still serializes and paces chunks. The alarm function skips overlapping runs. The two cron schedules still fire about 2,880 times per day in total. With the feature off and no batch secret provisioned, both return before DB initialization or paging. Keep the secret installed after stopping issuance so aging and stuck alerts remain active. Apply the migration before provisioning the secret. With no control row, status and export return `404 coupon_batch_not_provisioned`, and alarms do no work. The worker rechecks the originating expiring PAT, its desk grant and the deadline before minting a chunk.

A single batch over 3,000 and a Pacific day over 4,000 new intents create durable alerts, not refusals. Count new mint keys once in their owning batch’s acceptance day. Exhausted selector collisions stay on the original manifest; a new confirmed batch can regenerate the unminted intent. A replay that adds no new intents does not get the daily alarm mark. Track actual minted rows separately. The pager endpoint configured by `AIH_COUPON_BATCH_PAGE_URL` and `AIH_COUPON_BATCH_PAGE_TOKEN` must dedupe requests by `Idempotency-Key` before paging. Confirm that contract before rollout. A missing or failing pager leaves the outbox pending, without holding issuance. The worker pages once after a batch has been pending for 30 minutes, and separately if eight failed attempts at one chunk park the batch. There is no API to re-queue a parked batch. Recovery is a desk ruling: inspect the sanitized retry cause and export committed codes before deciding what to do. A stop past the export window refuses remaining mints. Do not discard the manifest or bypass the original expiry and grant checks.

Stop through the control rows, **not** by unsetting `AIH_COUPON_BATCH_ENABLED`. For a full stop, set `claimsEnabled=0` on `ai-hero-claims` first, then `enabled=0` on `ai-hero`, and wait for both commits. For issuance only, change just `enabled` on `ai-hero`. Admission and minting lock only the issuer row. Claims hold a shared lock on the separate claim row through the coupon transaction, so a slow issuer cannot hold up a customer. An in-flight claim can spend its coupon only before the claim stop commits. Status and authorized export remain available even while stopped. Existing purchases and entitlements stay valid. Reconcile the queue before re-enabling. Do not delete dedupe rows, reissue accepted keys through SQL or roll back paid settlement.

## C5 seat cap

With `AIH_COUPON_BATCH_ENABLED=true`, existing C5 seat-cap readers omit only direct, uncharged $0 purchases linked by `Purchase.couponId` to a C5 `batch-coupon-` row with the stored `couponBatchTemplate: c5-comp-v1` marker and no merchant coupon. Paid and discounted purchases, ordinary free coupons, and team orders and redemptions keep their existing counting rules. With the flag off, the old count still includes comps; capped C5 displays clamp remaining seats at zero. To stop issuance, always disable the control row, never the flag. Unsetting the flag also changes public seat counts and disables comp presentation. The Stripe handoff and ordinary free claims do not check the C5 seat cap on main; this change adds no enforcement there. Course Builder’s formatted-price response echoes the configured cap; the app’s pricing loader and availability endpoint supply remaining inventory.

Before using the flag, confirm whether the C5 cap is meant to bound real room size, such as live-session or Discord capacity. If it is, comps need a separate limit. This PR does not add one.

`pricing-decisions.seatsTaken` is a TypeScript specification with no production callers. Only `pricing-decisions.test.ts`, `seats-taken-query.mysql.test.ts`, and `coupon-batches/capacity.mysql.test.ts` call it. Production pricing and availability use `seats-taken-query.ts`; row-count readers use `purchase-count.ts` or apply the shared predicate to their existing count.

## Before enabling

Ledger’s deployment-only findings remain in this checklist: check the database and lock headroom, delivery, telemetry, cache behavior, and the credential and bearer lifecycle before rollout. Local fixes are not hosted proof.

- **Ledger 17 — C5 count load.** The flag-on C5 row-count path bypasses the persisted purchase-count cache, even with `quantityAvailable=-1`. Measure query volume, latency and database load for real C5 read traffic before enabling. Also verify the rare selector-collision index readback on the deployment database alongside the claim lock and worker session checks.
- **Course Builder rollout.** Verify checkout, webhook and video paths beyond loopback. Review upstream Course Builder port conformance; app fixtures do not replace that suite.
- **14 — Deployment database.** Prove the real `couponBatchRuntime` on a PlanetScale branch: the issuer's required session `SET` statements, retry after a rejected session, and status/export alongside a drain on the one-connection pool. Verify the claim control shared lock, coupon `FOR UPDATE`, and control-row stop acknowledgement on Vitess. Confirm the ordinary app pool reads the SDK's coupon timestamps in UTC and test claims just before and after expiry; the browser fixture is deliberately away from that boundary. After migration read `SHOW CREATE TABLE AI_CouponBatch` and verify `deadlineAt` has no `ON UPDATE` behavior. Do not enable until these paths pass.
- **15 — First claims and access.** Comp claims use the app’s organization policy and commit the first user, owner membership and purchase together. The wrapper busts the claimant’s access cache after commit. A rolled-back first claim leaves no user to repair. Check cohort and included-workshop access with hosted auth and real product config; local proof used a synthetic session cache, product configuration and email.
- **16 — Purge and revocation.** Approve a way to purge `AI_CouponBatchIntent.sealedCode` after the export window while preserving dedupe and audit data. The current code does not purge it. An operator holding the database and the batch secret could decrypt still-valid bearers after export closes. Before any wave, the desk and Switchboard must approve how to revoke a leaked bearer. A full stop pauses claim acceptance globally, not permanently; there is no per-code revoke API. Keep the secret through outstanding export windows. Redemption does not depend on it.
- **17 — Bearers in URLs.** Hold link delivery until the team verifies the first request, Vercel access logs, client analytics that capture `location.href`, and Sentry ingestion. Headers alone do not prove a bearer was never recorded.
- **18 — Shared issuer connection.** HTTP status/export and drain share a one-connection pool; reads also lock the PAT row. Measure queue and lock latency during a drain and confirm callers can tolerate it.
- **19 — Migration order.** Apply the schema before provisioning the batch secret. Otherwise the alarm cron can fail every minute even with minting disabled.
- **21 — Hosted delivery and telemetry.** Verify the hosted `after()` wake and cron fallback, pager receiver dedupe by `Idempotency-Key`, and sanitized Axiom and Sentry ingestion. No hosted proof was collected here.
- **E10 — Hosted Inngest run counts.** Prove run counts on hosted Inngest: use an approved synthetic paced backlog with overlapping cron, admission and continuation wakes. Record queued, executing, sleeping and terminal run counts across minutes. Prove paced no-progress wakes do not accumulate and the 40-chunk continuation drains while the cron is withheld. Step concurrency does not limit sleeping runs.
- **22 — Fail-first evidence.** Attach red and green receipts for the rollout-critical cases; do not substitute a passing run for evidence that the tests detect a broken guard.
- **23 — Database clock.** The volume, rollover, alarm, revocation and export-window suite uses an injected clock. Verify the same boundaries with the production `UTC_TIMESTAMP(3)` path; the single-batch fixture is not boundary proof.
- **24 — Lock and platform headroom.** Measure the control-row fence hold time for a 3,058-item request, contention with the five-second issuer lock wait and checkout, and the submit route’s platform execution limit. The 12,000-item loopback fixture submitted a roughly 0.5 MB body in under a second with 120 manifest inserts. Measure a maximum-size request against the declared 60-second limit on the hosted path; loopback does not predict platform or Vitess latency.
- **25 — Capacity and cache rollout.** Loopback covers flag-off clamping after paid seats sell. Check multi-instance behavior and stale public/cache entries across the flag change and control-row stop on the deployment platform.
- **26 — Desk client and support.** The desk accepted that every new batch returns `202`, even for one item; there is no inline path. The client must follow `Location` and wait for durable progress. Verify the unchanged support mint contract with the desk client.
- **27 — Provisioning.** Confirm the single issuing principal (intent keys are global), approve an expiring least-privilege PAT and grant, and verify readback. No tool provisions them yet. Verify stored commerce PAT scopes in the operator’s token listing. The generic auth reader accepts recognized companion scopes on the same record; commerce-only credentials stay in the desk API and neither form gains analytics or admin access from commerce scopes.
