# Desk C5 coupon batches

Off by default. The desk can issue C5 comps without a production database credential. The old support mint route is unchanged.

## Wire contract

All calls are under `/api/commerce/coupon-batches`. Send an expiring desk PAT in `Authorization: Bearer …`. Commerce scopes are not available through self-service PAT minting. A separate server-side desk grant controls `commerce:coupons:mint` and `commerce:coupons:read` for each principal.

1. `POST /preview` with `campaignRef`, `templateId: "c5-comp-v1"`, `template: { productId: "product-s00zs", percentageDiscount: 1, maxUses: 1, deadlineAt }` and `items: [{ intentKey }]`. `deadlineAt` is an absolute, whole-second instant in the next 30 days. The response includes normalized terms, counts, an initial page of verdicts and a confirmation receipt. Preview writes nothing.
2. Confirm the terms. `POST` the same manifest with `previewReceipt` and an `Idempotency-Key` header. The receipt binds the normalized body, desk principal and policy version for five minutes. New batches return `202` after the whole request is durable. Minting runs only in the worker. Follow `Location` or replay the same key and manifest. A different manifest under the same key conflicts. A replay of an accepted manifest needs no new receipt and returns status even while new admissions are paused.
3. `GET /{batchId}?cursor=N` for up to 100 outcomes and aggregate counts. `POST /lookup` with `{ intentKeys: [...] }` for at most 100 keys. A pending item is not unknown. Duplicate intent keys inside one manifest are invalid. If a batch cannot mint because its credential, policy, deadline or export window is no longer valid, unminted keys can be submitted again in a new confirmed batch with a new request key and valid terms. Status and lookup never return redemption codes.
4. `POST /export` with `{ batchId, cursor? }` after completion, or while the batch is stopped or parked. A stopped or parked export returns only codes already committed, never a code for pending work. Resume scanning from cursor zero after progress, because a previously queued row may have minted. Only the initiating desk principal can export, with the read grant and a valid PAT. The response is private and no-store. Codes stop exporting after 24 hours or coupon expiry, whichever comes first. A second batch that references the same intent cannot extend that window.

Codes transfer until spent or expired. The private client submits the code in the body of the existing `/api/coursebuilder/redeem/coupon` free claim, never in a checkout URL or Stripe metadata. When `AIH_COUPON_BATCH_ENABLED=true`, the C5 `?code=` presentation resolves a reserved bearer for the free claim dialog; only a reserved bearer gets private/no-store and no-referrer headers. The page deliberately does not clear the URL: sign-in redirects and the claim dialog may still need it. Do not enable link delivery until first-request host, access-log and browser capture are verified. Comp claims require `Content-Type: application/json` with a `productIds` array. Non-JSON requests with a comp selector are refused; ordinary claims retain Course Builder’s existing parsing. Do not copy codes into receipts, logs or support transcripts. Coupon refs in status are not selectors. The template owns the C5 sold-out bypass; a different product cannot borrow it.

## Enable and stop

Deployment, grants and live minting each need approval.

- Paid coupon backfill done (receipt `2026-11-27T03-20Z`): the desk counted 158 uses. Confirm the receipt before the dependency rollout.
- Before flipping the batch gates, verify no existing coupon ID or code, or purchase coupon reference, begins with `c5comp_`, `batch-coupon-`, or `c5hash_`. The desk’s read-only pre-check found zero coupons and zero purchase references.

Apply `src/db/migrations/20261126_ai_hero_coupon_batches.sql` through the reviewed schema path. Leave `AIH_COUPON_BATCH_ENABLED` unset and the `ai-hero` row in `AI_CouponBatchControl` absent or disabled until rollout. Store a strong, dedicated `AIH_COUPON_BATCH_SECRET` server-side for preview signing and export encryption. Do not rotate it during an active export window unless losing export access is acceptable; redemption does not depend on the key.

Admission persists the complete manifest atomically in statements of up to 100 rows before returning `202`. The manifest rows are not separate jobs. The worker expands only the next eligible chunk into mint candidates, drains at most 100 rows per transaction, and uses one DB connection per issuer process, separate from checkout. The issuer pool sets UTC, a 15-second server idle timeout, and a 5-second lock wait timeout, and closes idle client sockets before the server timeout. If a required session setting is rejected, the pool refuses to serve work until restarted. Validate these settings on the deployment database before turning on the flag. Customer claims use the normal application pool and a coupon-row transaction, with no new Vitess session variable or lock timeout. Verify the configured database supports that locking path before enabling claims. The control row sets `chunkSize` and `paceMs` without a redeploy. Change those before adding concurrency. A `202` batch survives missed wakes; a once-per-minute sweep finds due work. The drain and alarm functions each skip overlapping runs. The two cron schedules still fire about 2,880 times per day in total. With the feature off and no batch secret provisioned, both return before DB initialization or paging. Keep the secret installed after stopping issuance so aging and stuck alerts remain active. Apply the migration before provisioning the secret. With no control row, status and export return `404 coupon_batch_not_provisioned`, and alarms do no work. The worker rechecks the originating expiring PAT, its desk grant and the deadline before minting a chunk.

A single batch over 3,000 and a Pacific day over 4,000 new intents create durable alerts, not refusals. Count new intent keys once in their owning batch’s acceptance day. Track actual minted rows separately. The pager endpoint configured by `AIH_COUPON_BATCH_PAGE_URL` and `AIH_COUPON_BATCH_PAGE_TOKEN` must dedupe requests by `Idempotency-Key` before paging. Confirm that contract before rollout. A missing or failing pager leaves the outbox pending, without holding issuance. The worker pages once after a batch has been pending for 30 minutes, and separately if eight failed attempts at one chunk park the batch. There is no API to re-queue a parked batch. Recovery is a desk ruling: inspect the sanitized retry cause and export committed codes before deciding what to do. A stop past the export window refuses remaining mints. Do not discard the manifest or bypass the original expiry and grant checks.

For an immediate stop, set the DB control row’s `enabled` to `0` through the approved operator path. Wait for that write to commit: it shares the transaction fence with admission and minting. A chunk holding the fence can finish before the stop acknowledges, not after. Status, authorized export of committed codes (even from a stopped or parked batch), and existing redemptions stay available. Reconcile the queue before re-enabling. Do not delete dedupe rows, reissue accepted keys through SQL or roll back paid settlement.

## Before enabling

- **2, 5 — Course Builder rollout.** The workspace still has two resolved versions of utils and email. Verify checkout, webhook and video paths beyond the loopback proof. Review the upstream Course Builder port conformance results; this app’s fixtures are not a substitute for that suite.
- **6 — Deployment database.** Verify the issuer’s required session `SET` statements and the ordinary app pool’s claim `FOR UPDATE` on PlanetScale/Vitess. A rejected `SET` leaves the issuer unavailable until restart. Do not enable until both paths pass.
- **7 — Lock headroom.** Measure admission fence hold time for a 3,058-item manifest and contention with the five-second issuer lock wait, status/export credential locks, and checkout. Confirm the submit route’s platform execution limit; it declares no `maxDuration`.
- **10 — Revocation decision.** The desk and Switchboard must decide how to revoke a leaked bearer **before any wave**. Stopping issuance does not revoke issued codes. There is no revoke API; the only current remedy is an approved database operation. Do not infer authority to run it.
- **12, 15 — First claims and access.** Comp claims provision the first user and owner membership in the claim transaction but skip the app helper’s logging, session-access cache invalidation and repair enqueue. Verify a newly signed-in claimant’s cohort and included-workshop access on the real product config. The synthetic entitlement proof used mocked product config and email and did not assert the session-cache bust.
- **14, 17 — Desk authority.** Intent IDs are global, not principal-scoped. Confirm the single issuing principal before rollout; review cross-principal intent semantics before adding another. No operator tool provisions commerce PATs or grants yet. Approve the grant and expiring, least-privilege PAT path and verify readback.
- **16 — Hosted delivery.** Verify the `after()` wake and cron fallback with hosted Inngest. Confirm pager receiver deduplication by `Idempotency-Key` and verify a sanitized test alarm through the approved pager path.
- **18 — Desk client.** A new batch returns `202` even for one item. The client must follow `Location` and wait for durable worker progress before export. There is no inline mint path.
- **19 — Support compatibility.** Verify the existing support mint wire contract with the desk client before enablement; current fixtures do not assert it end to end. Ordinary direct redemption still follows the legacy behavior regardless of the batch flag. The comp template owns only its own C5 presentation bypass.
- **20 — Secret lifecycle.** Keep the same batch secret until all outstanding export windows expire. Rotating it mid-window can make existing export pages return `503`; issued bearer redemption does not depend on this secret.
