# Desk C5 coupon batches

Off by default. The desk can issue C5 comps without a production database credential. The old support mint route is unchanged.

## Wire contract

All calls are under `/api/commerce/coupon-batches`. Send an expiring desk PAT in `Authorization: Bearer …`. Commerce scopes are not available through self-service PAT minting. A separate server-side desk grant controls `commerce:coupons:mint` and `commerce:coupons:read` for each principal.

1. `POST /preview` with `campaignRef`, `templateId: "c5-comp-v1"`, `template: { productId: "product-s00zs", percentageDiscount: 1, maxUses: 1, deadlineAt }` and `items: [{ intentKey }]`. `deadlineAt` is an absolute, whole-second instant in the next 30 days. The response includes normalized terms, counts, an initial page of verdicts and a confirmation receipt. Preview writes nothing.
2. Confirm the terms. `POST` the same manifest with `previewReceipt` and an `Idempotency-Key` header. The receipt binds the normalized body, desk principal and policy version for five minutes. New batches return `202` after the whole request is durable. Minting runs only in the worker. Follow `Location` or replay the same key and manifest. A different manifest under the same key conflicts. A replay of an accepted manifest needs no new receipt.
3. `GET /{batchId}?cursor=N` for up to 100 outcomes and aggregate counts. `POST /lookup` with `{ intentKeys: [...] }` for at most 100 keys. A pending item is not unknown. Duplicate intent keys inside one manifest are invalid. If a batch cannot mint because its credential, policy, deadline or export window is no longer valid, unminted keys can be submitted again in a new confirmed batch with a new request key and valid terms. Status and lookup never return redemption codes.
4. `POST /export` with `{ batchId, cursor? }` after completion, or while the batch is stopped or parked. A stopped or parked export returns only codes already committed, never a code for pending work. Resume scanning from cursor zero after progress, because a previously queued row may have minted. Only the initiating desk principal can export, with the read grant and a valid PAT. The response is private and no-store. Codes stop exporting after 24 hours or coupon expiry, whichever comes first. A second batch that references the same intent cannot extend that window.

Codes transfer until spent or expired. The private client submits the code in the body of the existing `/api/coursebuilder/redeem/coupon` free claim, never in a checkout URL or Stripe metadata. The existing C5 `?code=` presentation also resolves the code for the free claim dialog; the response is private and no-store with no referrer, and the page clears the query in browser history after it mounts. Verify first-request host and access-log capture before enabling any link-delivery client. Use JSON or URL-encoded form for redemption; other body encodings are refused before Course Builder sees them. Do not copy codes into receipts, logs or support transcripts. Coupon refs in status are not selectors. The template owns the C5 sold-out bypass; a different product cannot borrow it.

## Enable and stop

Deployment, grants and live minting each need approval.

- Paid coupon backfill done (receipt `2026-11-27T03-20Z`): the desk counted 158 uses. Confirm the receipt before the dependency rollout.
- Before flipping the batch gates, verify no existing coupon ID or code, or purchase coupon reference, begins with `c5comp_`, `batch-coupon-`, or `c5hash_`. The desk’s read-only pre-check found zero coupons and zero purchase references.

Apply `src/db/migrations/20261126_ai_hero_coupon_batches.sql` through the reviewed schema path. Leave `AIH_COUPON_BATCH_ENABLED` unset and the `ai-hero` row in `AI_CouponBatchControl` absent or disabled until rollout. Store a strong, dedicated `AIH_COUPON_BATCH_SECRET` server-side for preview signing and export encryption. Do not rotate it during an active export window unless losing export access is acceptable; redemption does not depend on the key.

Admission persists the complete manifest atomically in statements of up to 100 rows before returning `202`. The manifest rows are not separate jobs. The worker expands only the next eligible chunk into mint candidates, drains at most 100 rows per transaction, and uses one DB connection per issuer process, separate from checkout. The issuer pool sets UTC, a 15-second idle timeout, and a 5-second lock wait timeout on its MySQL session. Validate those issuer session settings on the deployment database before turning on the flag. Customer claims use the normal application pool and a coupon-row transaction, with no new Vitess session variable or lock timeout. Verify the configured database supports that locking path before enabling claims. The control row sets `chunkSize` and `paceMs` without a redeploy. Change those before adding concurrency. A `202` batch survives missed wakes; a once-per-minute sweep finds due work. The drain and alarm functions each skip overlapping runs. With the feature off, the two cron schedules still fire about 2,880 times per day in total, but return before DB initialization or paging. The worker rechecks the originating expiring PAT, its desk grant and the deadline before minting a chunk.

A single batch over 3,000 and a Pacific day over 4,000 new intents create durable alerts, not refusals. Count new intent keys once in their owning batch’s acceptance day. Track actual minted rows separately. The pager endpoint configured by `AIH_COUPON_BATCH_PAGE_URL` and `AIH_COUPON_BATCH_PAGE_TOKEN` must dedupe requests by `Idempotency-Key` before paging. Confirm that contract before rollout. A missing or failing pager leaves the outbox pending, without holding issuance. The worker pages once after a batch has been pending for 30 minutes, and separately if eight failed attempts at one chunk park the batch. Check the sanitized retry cause and repair the underlying issue before resuming any parked batch. Do not discard its manifest or bypass the original expiry and grant checks.

For an immediate stop, set the DB control row’s `enabled` to `0` through the approved operator path. Wait for that write to commit: it shares the transaction fence with admission and minting. A chunk holding the fence can finish before the stop acknowledges, not after. Status, authorized export of committed codes (even from a stopped or parked batch), and existing redemptions stay available. Reconcile the queue before re-enabling. Do not delete dedupe rows, reissue accepted keys through SQL or roll back paid settlement.
